# 基础 AI 对话模块：通俗版任务拆解与验收表

日期：2026-05-26

这份文档的目的不是写概念，而是把“基础 AI 对话”拆成团队可以执行、可以测试、可以验收的任务。

本阶段只做这一件事：让老人可以和 AI 顺畅对话。先不做完整的 21 天回忆录、家庭互动大系统和复杂运营后台。

## 1. 一句话说明我们要做什么

我们要做一个稳定的老人端 AI 对话底座：

老人可以按按钮或说唤醒词开始说话，系统把语音转成文字，AI 根据老人信息和记忆回答，必要时联网查资料，回答时能读出来；如果老人中途插话，AI 要立刻停下听老人说；对话中产生的重要信息要稳定变成记忆，而不是靠 AI 随便返回几张卡片。

## 2. 把技术词翻译成人话

| 技术词 | 通俗解释 | 用户能感受到什么 |
|---|---|---|
| ASR | 把老人说的话转成文字 | 老人说“我今天想听天气”，系统能识别成文字 |
| TTS | 把 AI 的文字回答读出来 | AI 不只显示文字，还能开口说话 |
| VAD | 判断现在有没有人在说话 | 系统知道老人开始说话、停下来了，减少误触发 |
| 智能打断 | AI 正在读答案时，老人一说话，AI 立刻停 | 老人不用等 AI 说完，可以自然插话 |
| 语音唤醒 | 页面打开时，说指定词或点大按钮开始对话 | 老人不用找复杂入口，可以直接开始 |
| 记忆 | 从对话中记住稳定事实 | AI 下次知道老人喜欢什么、家人是谁、过去经历是什么 |
| 联网 | AI 需要最新信息时去搜索，并告诉用户来源 | 问天气、新闻、政策时，不靠编 |
| Agent 编排 | 把一个问题拆给不同模块处理 | 用户只看到一个 AI，但内部有记忆、联网、安全等模块协作 |
| Tool Broker | 所有联网工具的统一入口 | AI 不能偷偷联网；每次联网都有记录和来源 |

## 3. 我们不一开始做什么

这些先不做，避免把 MVP 做散：

- 不承诺浏览器关闭后的后台语音唤醒。Web 页面关了以后继续监听，需要原生 App 或硬件设备。
- 不先上复杂 Agent 框架。先把 SGX 自己的对话主流程做清楚，再决定是否引入 LangGraph、Mastra 这类框架。
- 不把网页内容直接当成记忆。联网查到的信息只用于本轮回答，不能直接写进老人长期记忆。
- 不把敏感信息直接长期保存。健康、家庭矛盾、财务等内容必须有确认或保护策略。

## 4. 成熟开源项目怎么用

| 方向 | 可参考项目 | 我们怎么用 |
|---|---|---|
| 浏览器语音 | [MDN Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API) | 作为 Demo 和低成本 fallback，但不能完全依赖它做稳定生产语音 |
| 本地 ASR | [whisper.cpp](https://github.com/ggerganov/whisper.cpp)、[faster-whisper](https://github.com/SYSTRAN/faster-whisper) | 后续可做本地/私有化语音识别；MVP 先把 ASR 接口设计好 |
| 一体化离线语音 | [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) | 适合后续老人端设备、本地服务或隐私要求更高的部署 |
| VAD/打断 | [Silero VAD](https://github.com/snakers4/silero-vad) | 用来判断老人是否开始说话，是智能打断的关键 |
| 本地 TTS | [Piper](https://github.com/rhasspy/piper) | 可参考或做后续本地 TTS；MVP 先做 TTS provider 接口 |
| 唤醒词 | [openWakeWord](https://github.com/dscripka/openWakeWord)、[livekit-wakeword](https://github.com/livekit/livekit-wakeword) | 用于“页面打开时”的前台唤醒；不承诺后台常驻 |
| 联网搜索 | [SearXNG](https://docs.searxng.org/) | 可作为自建搜索入口；所有搜索必须经过 Tool Broker |
| 网页正文抽取 | [Mozilla Readability](https://github.com/mozilla/readability) | 把网页正文提取出来，同时标记为“不可信外部内容” |
| Agent 编排参考 | [LangGraph.js](https://langchain-ai.github.io/langgraphjs/)、[Mastra](https://mastra.ai/framework)、[AI SDK](https://ai-sdk.dev/docs/providers) | 先参考设计思想，不急着重度引入 |
| 长期记忆参考 | [Mem0](https://github.com/mem0ai/mem0)、[pgvector](https://github.com/pgvector/pgvector) | MVP 先做结构化记忆，后续再升级数据库和向量检索 |

## 5. 推荐开发顺序

不要先从语音开始堆功能。更稳的顺序是：

1. 先把“文字对话 + 记忆 + Agent 编排”做稳定。
2. 再把“语音输入 + 语音播报 + 智能打断”做稳定。
3. 再把“联网搜索 + 来源引用 + 安全权限”接进去。
4. 最后做“前台语音唤醒”和完整体验验收。

原因很简单：如果文字对话、记忆和联网逻辑都不稳定，语音只会把问题放大，调试会很痛苦。

## 7. 每个版本完成后到底应该长什么样

### v0.1 完成后的样子

用户还不一定用语音，但文字聊天应该稳定：

- AI 会根据老人资料和已有记忆回答。
- AI 会稳定提取记忆，不再靠 `suggestedCards`。
- 记忆有来源，能确认、修改、删除。
- Prompt 和 Agent 不再全混在一个接口里。
- 每次改 prompt 或记忆逻辑，都能跑固定测试集。

### v0.2 完成后的样子

老人可以真实用语音聊天：

- 老人按按钮开始说话。
- 系统识别老人语音。
- AI 回复并读出来。
- AI 说话时老人插话，AI 能停下。
- 连续 10 轮对话不会乱状态。

### v0.3 完成后的样子

AI 可以受控联网：

- 需要最新信息时才联网。
- 联网前后都有日志。
- 回答带来源。
- 外部网页内容不能影响系统指令。
- 页面打开时可以用唤醒词或大按钮开始。

## 8. 团队怎么专业协作

不是一定要硬分成很多人，而是每个任务都必须覆盖这些专业动作：

| 专业动作 | 具体怎么做 |
|---|---|
| 产品确认 | 每个任务都写清楚用户能看到什么变化 |
| 架构设计 | 先定义接口、状态、数据结构，再写代码 |
| AI 算法 | ASR/TTS/VAD/记忆/联网意图都要有测试样例和指标 |
| 前端体验 | 老人端按钮要大，状态要清楚，出错要能恢复 |
| 后端工程 | 每个模块独立，失败有错误码，日志能追踪 |
| QA 测试 | 每个任务先写验收用例，再实现 |
| 安全隐私 | 外部网页、联网、音频、记忆、密钥都要有边界 |

如果用多智能体模式，建议这样拆：

- 一个智能体负责代码现状梳理。
- 一个智能体负责开源方案和技术选型。
- 一个智能体负责测试和验收指标。
- 主智能体负责合并判断、写设计、执行修改和最终验收。

## 9. 下一步最应该做什么

下一步不要直接装语音库，也不要直接改 UI。先做 v0.1 的第 1 到第 4 个 P0：

1. 冻结基础对话范围。
2. 画出完整对话流程。
3. 定义对话状态机。
4. 拆出 Agent 职责和 Prompt 管理方式。

这四件事做完后，再开始改 `/api/chat`。这样后面做语音、联网、记忆时，才不会继续堆成一个难维护的大函数。
